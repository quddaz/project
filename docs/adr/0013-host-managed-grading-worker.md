# ADR 0013: 호스트 관리형 채점 워커

- 상태: Accepted
- 날짜: 2026-07-22
- 관련 결정: ADR 0003, ADR 0007, ADR 0011

## 배경

채점 워커는 제출 저장소를 임시 작업 공간에 내려받고 Docker 샌드박스를 실행한다. Docker Compose의 워커 컨테이너에 Docker 소켓을 마운트하면 구현은 간단하지만, 해당 컨테이너가 호스트 Docker 데몬을 제어할 수 있어 컨테이너 격리만으로는 권한 경계를 지키기 어렵다.

## 사용자 가치

사용자는 제출 코드가 네트워크와 자원 제한이 적용된 샌드박스에서 실행된다는 신뢰를 얻는다. 운영자는 API와 데이터베이스를 한 번의 Compose 명령으로 관리하면서도 채점 실행 권한을 명확히 분리할 수 있다.

## 결정

초기 운영 환경에서 Docker Compose는 MySQL과 API만 기동한다. 채점 워커는 Docker CLI와 소켓 접근 권한을 가진 전용 호스트 프로세스로 실행한다. `./gradlew workerRun`은 동일한 애플리케이션 JAR의 워커 전용 진입점으로 동작하며, API와 같은 MySQL에 연결한다.

로컬 검증은 `SECURITY_ENABLED=false`로 API와 MySQL을 Compose에서 기동하고, 호스트 워커가 공개 GitHub 저장소와 로컬 Docker 샌드박스를 사용해 작업을 처리하는 방식으로 수행한다. OAuth 실사용 검증은 GitHub OAuth 앱 자격 증명이 준비된 별도 단계로 둔다.

## 선택 이유

- Docker 소켓을 컨테이너에 노출하지 않아 워커 프로세스의 권한 경계를 명확히 한다.
- 채점 컨테이너의 `--network none`, CPU, 메모리, PID, 실행시간 제한은 그대로 유지한다.
- 단일 Spring 프로젝트와 워커 전용 진입점이라는 ADR 0011의 구조를 그대로 사용한다.
- API와 MySQL은 Compose의 MySQL 헬스체크와 API의 의존성 대기 설정으로 기동 순서를 관리한다.

## 검토한 대안

- 워커 컨테이너에 Docker 소켓 마운트: Compose만으로 모두 기동할 수 있지만 호스트 Docker 제어 권한을 부여한다.
- Docker-in-Docker: 별도 데몬을 둘 수 있지만 이미지 캐시와 권한, 중첩 컨테이너 관리가 복잡해진다.
- Kubernetes Job: 강한 운영 격리와 확장성을 제공하지만 MVP의 운영 복잡도가 과도하다.

## 검증 기준

- `docker compose up`으로 MySQL과 API가 정상 기동된다.
- 호스트에서 실행한 `workerRun`이 MySQL 작업을 선점한다.
- 워커가 시작한 채점 컨테이너에 네트워크, CPU, 메모리, PID 제한이 적용된다.
- OAuth 자격 증명 없이도 로컬 개발용 보안 비활성화 프로필에서 문제 조회와 채점 API를 검증할 수 있다.

## 결과

운영 서버에는 Docker CLI와 Docker 데몬 접근 권한을 가진 전용 워커 실행 계정이 필요하다. 워커의 로그, 재시작, 배포는 Compose 서비스가 아닌 시스템 서비스 또는 프로세스 관리 도구로 관리한다.
