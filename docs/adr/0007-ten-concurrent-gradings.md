# ADR 0007: 단일 서버 동시 채점 10건

- 상태: Accepted
- 날짜: 2026-07-21
- 관련 결정: ADR 0001의 초기 용량 목표를 구체화함

## 배경

ADR 0001은 초기 베타를 동시 채점 1~3건으로 가정했다. 실제 MVP는 여러 사용자가 같은 시점에 과제를 제출할 수 있으므로, 단일 Linux 서버에서 채점 10건을 동시에 처리할 수 있어야 한다. 채점 부하가 웹 API와 MySQL의 응답성을 훼손해서는 안 된다.

## 사용자 가치

10명이 동시에 제출해도 앞선 몇 건이 끝날 때까지 오래 기다리지 않고 바로 채점을 시작할 수 있다. 채점이 몰린 순간에도 문제 목록과 자신의 진행 상태를 정상적으로 확인할 수 있다.

## 결정

워커에 설정 가능한 실행 슬롯을 두고 기본값을 10으로 설정한다. 워커는 빈 슬롯이 있을 때만 MySQL 작업을 선점한다. 단일 서버의 시작 권장 사양은 12 vCPU, RAM 16GB 이상이며 채점 컨테이너 하나당 CPU 1코어, 메모리 1GB, 실행시간 120초를 기본 한도로 적용한다. API와 MySQL에는 최소 2 vCPU와 4GB 메모리를 예약한다.

11번째 이상의 작업이나 순간적인 자원 부족은 실패 처리하지 않고 `QUEUED` 상태로 유지한다. 워커를 여러 서버로 확장할 때는 서버별 슬롯 수의 합을 전체 용량으로 관리한다.

## 선택 이유

- 슬롯 방식은 실행 중인 컨테이너 수를 명시적으로 제한한다.
- 작업을 실행 직전에 선점하므로 긴 작업이 DB lease를 불필요하게 점유하지 않는다.
- API와 MySQL의 예약 자원을 보장해 채점 부하와 사용자 요청을 격리한다.
- 현재 목표에는 별도 오케스트레이션 클러스터 없이 단일 서버로 대응할 수 있다.

## 검토한 대안

- 동시 채점 1~3건 유지: 운영비는 낮지만 10명 동시 제출 목표를 충족하지 못한다.
- 자원과 무관하게 제출 즉시 컨테이너 실행: 과부하 시 전체 서비스 장애로 이어질 수 있다.
- 처음부터 Kubernetes 실행 클러스터 사용: 확장성은 높지만 MVP 운영 복잡도가 과도하다.

## 검증 기준

- 서로 다른 사용자 10명의 제출이 모두 실행 슬롯을 획득한다.
- 채점 부하 중 문제 목록 및 제출 상태 조회 API의 p95 응답시간이 500ms 이내다.
- 11번째 작업은 실패하지 않고 큐에서 대기하며 슬롯 반환 후 실행된다.
- 컨테이너별 CPU, 메모리, 시간 제한이 실제 부하 테스트에서 적용된다.

## 결과

초기 서버 비용과 Docker 이미지·Gradle 캐시가 사용하는 디스크 용량이 증가한다. 문제별 실제 메모리와 실행시간을 관측해 기본 한도를 조정해야 한다. 단일 서버 한계에 도달하면 API 구조를 바꾸지 않고 워커 서버를 분리한다.
