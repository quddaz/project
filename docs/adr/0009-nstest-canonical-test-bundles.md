# ADR 0009: NsTest 공식 테스트 번들

- 상태: Accepted
- 날짜: 2026-07-22
- 관련 결정: ADR 0003의 런타임 테스트 주입 형식을 구체화함

## 배경

프리코스 문제는 `Application.main`, 랜덤값 통제, 표준 출력 캡처, 예외 검증을 함께 사용하는 `NsTest` 관례에 맞춰 작성된다. 사용자가 fork한 저장소의 테스트는 수정할 수 있으므로 최종 채점 기준으로 신뢰할 수 없다.

## 사용자 가치

사용자는 실제 프리코스와 같은 `ApplicationTest` 작성 방식으로 로컬 피드백을 받을 수 있다. 서버는 모든 제출에 같은 공식 테스트를 적용하므로 테스트 수정 여부와 관계없이 결과가 일관된다.

## 결정

공식 테스트 번들은 문제 버전별 `ApplicationTest.java`와 필요한 `NsTest` 지원 코드를 포함한다. 워커는 제출 commit SHA를 checkout한 후 공식 테스트를 `src/test/java/ApplicationTest.java`에 주입하고 `./gradlew test --tests ApplicationTest`를 실행한다.

공식 테스트는 `run(...)`, `output()`, `runException(...)`, `assertRandomNumberInRangeTest(...)`로 입력·출력·예외·랜덤 동작을 검증한다. 테스트 assertion이 최종 판정을 결정하며 워커는 Gradle 테스트 결과와 제한된 출력·실패 요약만 저장한다.

## 선택 이유

- 우아한테크코스 프리코스의 테스트 작성 경험과 일치한다.
- 입력·기대 출력·예외·랜덤값을 하나의 테스트 시나리오에서 표현할 수 있다.
- 사용자 저장소의 테스트 변경이 서버 기준을 우회하지 못한다.
- 기존 Docker/Gradle 고정 실행 환경과 자연스럽게 결합된다.

## 검토한 대안

- YAML stdin/stdout 시나리오만 사용: 단순하지만 `NsTest`의 랜덤 제어와 예외 검증을 재현하기 어렵다.
- 사용자 fork의 테스트만 실행: 테스트 삭제·수정으로 채점을 조작할 수 있다.
- 별도 실행 스크립트마다 채점: 문제별 환경 차이가 생기고 고정 계약이 깨진다.

## 결과

공식 테스트 번들을 문제 버전과 함께 관리해야 하며, 채점 이미지는 `NsTest`와 Gradle 의존성을 제공해야 한다. 테스트 소스와 출력은 비신뢰 제출 코드와 함께 실행되므로 기존 Docker 권한·네트워크·자원 제한을 그대로 적용한다.
