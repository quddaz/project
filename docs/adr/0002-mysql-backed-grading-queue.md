# ADR 0002: MySQL 기반 채점 작업 큐

- 상태: Accepted
- 날짜: 2026-07-21

## 배경

채점은 비동기로 실행되어야 하지만 초기 규모에서 Redis나 별도 메시지 브로커를 함께 운영하면 장애 지점과 관리 비용이 늘어난다. 제출과 작업 생성은 항상 함께 성공하거나 실패해야 한다.

## 사용자 가치

서버가 재시작되어도 제출이 사라지지 않고, 제출은 접수됐지만 채점 작업이 없는 불일치를 줄인다. 초기 운영 비용을 낮춰 핵심 학습 기능에 집중할 수 있다.

## 결정

MySQL의 `grading_jobs` 테이블을 작업 큐로 사용한다. 제출과 작업은 한 트랜잭션으로 생성하고 워커는 `FOR UPDATE SKIP LOCKED`로 실행 가능한 작업을 선점한다. lease 만료와 최대 3회 재시도를 지원한다.

## 선택 이유

- MySQL 하나로 데이터 정합성과 작업 내구성을 관리한다.
- 행 잠금으로 여러 워커의 중복 선점을 방지한다.
- 현재 처리량에서는 전용 브로커의 이점보다 운영 비용이 크다.

## 검토한 대안

- 인메모리 큐: 재시작 시 작업을 잃고 수평 확장이 어렵다.
- Redis: 빠르지만 초기 운영 구성과 트랜잭션 정합성이 복잡해진다.
- Kafka 또는 RabbitMQ: 기능과 운영 부담이 현재 규모보다 크다.

## 결과

작업 선점 쿼리는 MySQL에 종속되며 Testcontainers MySQL로 동시성을 검증해야 한다. 처리량이나 DB 부하가 임계점을 넘으면 작업 저장소 인터페이스 뒤에서 전용 큐로 교체한다.
