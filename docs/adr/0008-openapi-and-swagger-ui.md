# ADR 0008: OpenAPI 명세와 Swagger UI

- 상태: Accepted
- 날짜: 2026-07-21

## 배경

REST API는 최소 화면뿐 아니라 향후 별도 프론트엔드와 운영 도구에서도 사용될 수 있다. 문서가 코드와 분리되면 요청·응답, 오류 코드, 인증 요구사항이 실제 구현과 달라질 가능성이 높다.

## 사용자 가치

API 사용자는 실행 가능한 문서에서 요청 형식과 결과를 즉시 확인할 수 있다. 개발자는 프론트엔드와 연동할 때 추측을 줄이고, 오류 응답과 인증 조건을 일관되게 이해할 수 있다.

## 결정

Spring Boot 4와 호환되는 springdoc-openapi 3.x를 사용해 OpenAPI 3.1 JSON과 Swagger UI를 제공한다. 공개 REST 컨트롤러에는 작업 요약, 입력 제약, 성공 응답, 공통 오류 응답과 enum 값을 문서화한다. 운영 환경에서도 문서를 제공하지만 채점 내부 API와 관리용 엔드포인트는 명세에서 제외한다.

## 선택 이유

- 런타임 컨트롤러와 DTO를 기반으로 명세를 생성해 문서 불일치를 줄인다.
- Swagger UI에서 API를 탐색하고 공개 요청을 직접 검증할 수 있다.
- OpenAPI 문서는 향후 클라이언트 생성과 계약 검증에 재사용할 수 있다.

## 검토한 대안

- 수동 Markdown API 문서: 읽기 쉽지만 구현과 동기화하기 어렵다.
- 별도 OpenAPI 우선 설계 파일: 계약 중심 개발에는 좋지만 MVP에서 코드와 명세를 이중 관리해야 한다.
- 문서 미제공: 초기 구현은 빠르지만 프론트엔드 연동과 운영 진단 비용이 커진다.

## 결과

API 변경 시 OpenAPI 인수 테스트와 문서 어노테이션을 함께 갱신해야 한다. Swagger UI 공개 범위는 Spring Security 설정에서 명시적으로 관리하고, 내부 정보나 채점 실행 세부사항을 스키마와 예시에 포함하지 않는다.
